What is Ansible?

Module 1, Lesson 1 · ~7 minutes

The win By the end you can point at the cloudio repo and say: this machine runs Ansible, that machine gets configured, this file is the list, and that file is the plan — and explain why re-running the plan is safe.

The one-sentence version

Ansible is a tool that logs into other machines over SSH and makes them match a description you wrote. The description lives in plain-text files you keep in git. That's it. Everything else is detail.

The official docs put it this way: Ansible lets you “declare the desired state of a local or remote system” and then “ensures that the system remains in that state.”1

Why cloudio needs it

Your plan is: install Proxmox on the Vaio by hand once, then run one command from your MacBook and have the whole server build itself — the Home Assistant VM, the two LXC containers, Docker, the media stack, UniFi, Tailscale, the backups. That "one command" is Ansible reading ansible/site.yml and doing the work over SSH.

If the Vaio dies, you buy another mini-PC, install Proxmox, run the same command, restore the backups, and you're back. The repo is the server, written down.

The four nouns

Ansible has a small vocabulary. Four words carry most of it:

Control node The machine that runs Ansible. Your MacBook. Nothing about Ansible is permanently installed on the machines it manages — the control node is where the tool and the repo live.2
Managed node A machine Ansible changes, reached over SSH. Here that's the Vaio, which the repo calls pve. It just needs sshd running and Python present — both already true on a fresh Proxmox install.
Inventory The list of managed nodes, organised into groups. File: ansible/inventory.yml. cloudio's is tiny — one host.
Playbook The plan: an ordered list of things to make true, in YAML. File: ansible/site.yml. "Playbooks automate your tasks" using “YAML syntax for code that reads like documentation.”1

See it in the repo

ansible/inventory.yml — the list

proxmox:
  hosts:
    pve:
      ansible_host: "{{ pve_ip }}"
      ansible_user: root

One group (proxmox), one host (pve), reachable at an address (pve_ip, set in your vars) as the root user. That's the entire inventory.

ansible/site.yml — the plan

- name: Cloudio home server
  hosts: proxmox            # ← which machines (a group from the inventory)
  gather_facts: true

  roles:                    # ← what to do to them, in order
    - role: proxmox_base
    - role: haos_vm
    - role: media_lxc
    - role: unifi_lxc

"For every host in the proxmox group, apply these four roles in order." A role is just a folder of tasks bundled for reuse — Lesson 6 opens one up. A task is one step; it calls one module (a small program like apt or copy that knows how to make one kind of change). You'll meet those properly in Lessons 4 and 7.

The idea that shapes everything: idempotency

Run ansible-playbook site.yml once, or ten times in a row — the Vaio ends up in the same state. Ansible checks each step before acting: “when the system is in the state your playbook describes, Ansible does not change anything, even if the playbook runs multiple times.”1

Why you'll care You will edit a role, re-run the whole playbook, see changed on just the one task you touched and ok on everything else, and move on. No "rebuild from scratch". That fast edit-and-re-run loop is only possible because Ansible is idempotent — and it's why cloudio chose Ansible over a pile of shell scripts (see ADR-0003).

What Ansible is not, here

  • Not a service running on the Vaio. It's “agent-less” — it connects, works, disconnects.1 The Vaio never knows Ansible exists between runs.
  • Not a central server. The control node is just wherever you typed the command. Today that's your Mac.
  • Not Terraform. There's no state file describing what Ansible thinks it built. "Is the server correct?" is answered by running the playbook again and watching for changed.
