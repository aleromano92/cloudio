The control node: ansible.cfg & collections

Module 1, Lesson 2 · ~7 minutes

The win By the end you can explain what ansible.cfg actually does, why you always cd ansible before running a command, and — with evidence from this repo, not a guess — which modules need a collection installed and which don't.

The one-sentence version

ansible.cfg is a **project's settings file** — it tells Ansible where the inventory, roles, and extra modules live, so you stop typing the same flags every time. A collection is an installable pack of extra modules and plugins; ansible.builtin is the set that ships with Ansible itself and needs nothing installed.

Why cd ansible matters

Every command you've run so far started with cd ansible. Here's why that's not just about relative file paths: Ansible looks for a config file in a fixed order and uses only the first one it finds — the rest are ignored:

  1. ANSIBLE_CONFIG environment variable, if set
  2. ansible.cfg in the current directory
  3. ~/.ansible.cfg in your home directory
  4. /etc/ansible/ansible.cfg

"Ansible will process the above list and use the first file found, all others are ignored."1 Run the command from anywhere else and cloudio's ansible.cfg is invisible — Ansible silently falls back to built-in defaults instead.

cloudio's ansible.cfg, line by line

ansible/ansible.cfg

[defaults]
inventory = inventory.yml
roles_path = roles
collections_path = collections
host_key_checking = True
retry_files_enabled = False
interpreter_python = auto_silent
timeout = 30

[ssh_connection]
pipelining = True
inventoryThe default inventory file — no -i flag needed on every command.
roles_pathWhere role folders are searched for. It's why site.yml can say role: proxmox_base and Ansible finds roles/proxmox_base/.
collections_pathInstalled collections live in ansible/collections/ — project-local and gitignored — instead of the global ~/.ansible/collections. Clone the repo on a new machine, get exactly these versions.
host_key_checkingTrue — refuse to connect if the host's SSH key isn't already trusted. This is exactly why Phase 0 had you run ssh root@<ip> by hand once before Ansible would touch the box.
retry_files_enabledFalse — don't litter a .retry file listing failed hosts after a bad run. Not useful for a one-host repo.
interpreter_pythonauto_silent — auto-detect which Python binary to use on pve, without warning spam.
timeoutSSH connection timeout, in seconds.
pipeliningTrue — fewer SSH round-trips per task, so runs are noticeably faster.

Collections & FQCNs

"Collections are a distribution format for Ansible content that can include playbooks, roles, modules, and plugins."2 Every module is referred to by its fully-qualified collection name: namespace.collection.module — e.g. ansible.posix.mount.

ansible.builtin is the one namespace that's special: those modules ship inside Ansible itself.3 No install, ever. Anything else — ansible.posix.*, community.general.* — has to be installed first, which is what requirements.yml is for:

ansible/requirements.yml

collections:
  - name: ansible.posix
    version: ">=1.5.0"
  - name: community.general
    version: ">=8.0.0"

ansible-galaxy collection install -r requirements.yml reads this and installs both, pinned, into ansible/collections/ (per collections_path above). Skip it, and the first task that needs ansible.posix.mount fails with "couldn't resolve module" — the playbook doesn't silently work around a missing collection.

The reveal: what's actually used

Two collections are installed. How much of each does the repo actually call? This is measured, not guessed — every FQCN across all four roles, counted: 

$ grep -rhoE '\b(ansible\.builtin|ansible\.posix|community\.general)\.[a-zA-Z_]+' roles/ \
    | sort | uniq -c | sort -rn

  28 ansible.builtin.command
   6 ansible.builtin.import_tasks
   5 ansible.builtin.template
   4 ansible.builtin.systemd
   4 ansible.builtin.debug
   3 ansible.builtin.shell
   3 ansible.builtin.replace
   3 ansible.builtin.get_url
   3 ansible.builtin.file
   3 ansible.builtin.apt
   2 ansible.builtin.copy
   1 ansible.posix.sysctl
   1 ansible.posix.mount
   1 ansible.builtin.pipe

Notice community.general — installed, pinned in requirements.yml — has zero uses. Every task is ansible.builtin (mostly command, driving pct/qm/docker directly) plus exactly two calls into ansible.posix (a mount, a sysctl). This is ADR-0003 made visible: the repo chose native CLIs over Proxmox-specific modules — so the collection built for that never got used. It stays installed for when the repo does need it.

One version: "ansible.cfg is the project's settings file — it tells Ansible where to find the inventory, the roles, and the installed extra modules, so we don't retype those paths every run.
