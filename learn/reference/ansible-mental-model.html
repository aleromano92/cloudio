Ansible mental model

One page. The nouns and the one-line rule. Print it.

The picture

ansible-playbook site.yml is the whole sequence: Ansible reads the plan, connects over SSH, makes the node match it, and disconnects.

The nouns

Control nodeWhere Ansible runs. Your Mac. Never listed in the inventory.
Managed nodeA machine Ansible changes. Reached over SSH. Here: pve.
InventoryThe list of managed nodes, in groups. File: ansible/inventory.yml.
PlaybookAn ordered plan in YAML. File: ansible/site.yml.
PlayOne block inside a playbook: "these hosts get these roles/tasks".
TaskOne step. Calls exactly one module.
ModuleThe unit of work (apt, copy, template, command…). Ships the "make it so" logic.
RoleA reusable folder of tasks + files + templates + handlers. Here: proxmox_base, haos_vm, media_lxc, unifi_lxc.
CollectionA distributable bundle of modules/roles from Galaxy. Here: ansible.posix, community.general.

The one rule that explains the style

Idempotency Running the playbook once and running it ten times leave the node in the same state. A task only reports changed when it actually changed something. This is why cloudio can re-run site.yml after every small edit instead of rebuilding from scratch.

What is NOT here

  • No agent/daemon on the managed node. Just SSH + Python.
  • No central server. The control node is wherever you run the command.
  • No state file. "Is reality correct?" is answered by re-running (contrast: Terraform).

Sources: Introduction to Ansible, Getting started with Ansible (Ansible Community Documentation).
